    How does an LSM tree store two values for one key?

    Suppose you save cedar = sage and later change the value to jade. The diagram shows both values. How can the database answer a read while the old value is still on disk?

    A log-structured merge tree (LSM tree) collects changes in memory so it can write many keys to disk together. Updating each key’s place on disk immediately would scatter a batch of writes across many locations. Batching lets the engine write ordered stretches of data. The price is that changes to the same key can end up in different places. Follow cedar through a write, a read, and a merge to see how the engine keeps those versions straight. The original paper describes this batching idea using a memory component and a rolling merge into a disk component. O’Neil et al., section 2

    1. Write a value and keep a way to recover it

    Look at write #03 in the example’s history. The key is cedar, the value is sage, and the number records when this write arrived. The engine first appends the change to the write-ahead log (WAL). It then places the value in a table in memory called the memtable. A read can now find the value in RAM. If a crash clears RAM, the engine can replay the saved log entry. The history in the diagram lets you revisit old writes even after their log entries have been retired. RocksDB on WAL recovery

    Create, update, and delete a key

    In the Client stage, click INSERT to run INSERT INTO records (key, value) VALUES ('juniper', 'needles');. Step through the lookup first. If the key is absent, the engine appends a numbered record to the WAL and puts it in the memtable. Creating the same key again stops at the existence check.

    Run UPDATE records SET value = 'pine' WHERE key = 'juniper';. Once the lookup finds the current key, the engine appends a newer version. A read now returns pine, even if an SSTable still contains needles.

    Run DELETE FROM records WHERE key = 'juniper';. The engine appends a deletion marker called a tombstone. Run SELECT * FROM records WHERE key = 'juniper'; to see why the tombstone yields zero rows. The WAL can replay the marker after a crash. A flush copies it to disk, and this sandbox retains the newest tombstone during compaction so an older file cannot bring the key back. Create the key again to give it a newer live version.

    2. Flush a batch into a sorted file

    The first three writes arrived in the order maple, birch, cedar. Once the engine freezes that batch, it writes the records in key order instead: birch, cedar, maple. This produces run-001.sst, a sorted string table, or SSTable. Its contents stay fixed. Once the file is installed, the engine can retire the log entries it covers and reuse the memory. A second batch later fills another file. LevelDB’s description of logs and sorted tables

    A database usually schedules a flush when a write pushes the memtable over its memory budget. New writes go into a fresh memtable while a background worker writes the frozen one to disk. In RocksDB, total memory pressure or a WAL that grows past its limit can trigger a flush earlier. The sandbox uses a small budget so you can cross it with a few writes. It counts the UTF-8 bytes in the current memtable keys and values. Click Pause, then Next step to follow the write into its automatic flush. RocksDB flush triggers

    3. Update the same key and follow a read

    Write #07 sets cedar = jade. It goes through the log and into the current memtable. The earlier file still holds sage. The operation controls open on the snapshot after write #08. Reset example restores that snapshot.

    Follow the cedar read in the walkthrough below. Where can the engine stop? It checks memory first, finds #07, and returns jade. Every installed file in this example contains an earlier batch, so probing more files cannot turn up a later write. If memory misses, the engine tries the files from newest to oldest. For maple, the search passes through memory and the second file before it reaches the first.

    Each SSTable in Read sources has a Bloom filter. When a flush or merge creates a file, every key in it sets two bits, including keys with tombstones. A read tests those same bits. One clear bit proves the key is absent and the engine skips the file. If both are set, the engine checks the rows. Other keys can set those bits too, so a possible match can still turn out to be absent. Watch the filters during a juniper read ↑ · Build a Bloom filter step by step →

    5. Merge files and decide which version survives

    Choose Engine → Compact. Imagine reading the sorted inputs side by side, taking the smallest remaining key from any input. When you reach cedar, two records compete for one place in the output. The engine keeps #07 (jade) and drops #03 (sage). It installs the merged file, and later reads use that file. This example merges all installed files and serves only current values, so no reader needs #03.

    Try a read for juniper, a key nobody wrote. After compaction, the engine can establish its absence by checking memory and one Bloom filter. Immediately after the flush in step 4, it consulted three file filters after the memory miss. That shorter search cost work up front: compaction read records and wrote a new file, even for keys such as maple whose value never changed.

    When does compaction start, and which SSTables should merge?

    Compare both policies on the same four files ↑

    Each flush adds an SSTable. That new file can push a tier or level across its compaction threshold. The database can then queue a merge while foreground reads and writes continue. The sandbox shows the work in sequence and uses the selected policy to choose its input files. Switching policies shows the same commands under the other layout.

    Size-tiered compaction groups SSTables with similar sizes on disk. Cassandra’s size-tiered strategy normally waits for four files in a group. Four 64 MiB files can merge while an older 512 MiB file waits. This avoids repeatedly rewriting the large file with every flush, but both files may still contain versions of cedar. Cassandra’s size-tiered strategy

    Leveled compaction organizes files into levels with increasing size budgets. In LevelDB, files in level 0 can overlap. A file-count threshold triggers compaction at level 0. In deeper levels, the trigger is a byte budget and the key ranges within each level are disjoint. Moving a file down means merging it with the overlapping files in the destination level. Rewriting those ranges costs writes, but a read for juniper can narrow its search to at most one candidate file in each deeper level. LevelDB’s file layout
