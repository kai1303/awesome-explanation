    Why does key 17 end up in slot 3?

    A hash table uses a key to work out where to start looking. Imagine inserting key 17 into a table with four slots numbered 0 through 3. Slot 1 holds 5 and slot 2 holds 6. Two slots are empty. Which one should receive 17 so we can find it again?

    This table stores distinct integer keys directly in its slots. For this example its size stays fixed, and no keys are deleted. We will compute a starting slot, inspect one slot at a time, and write 17 once.

    Start with key 17 ↑

    Find the home slot

    Divide 17 by 4. Four groups of four account for 16, leaving a remainder of 1. Our hash function uses that remainder as the home slot. Key 5 has the same remainder. When two different keys share a home slot, we have a collision.

    Predict the first slot ↑

    Inspect one neighbor at a time

    A probe is one inspection of a slot. At slot 1, compare the incoming 17 with the resident 5. They differ, so 5 stays where it is and we check slot 2. There we find 6. The same rule sends us to slot 3. This is linear probing. Each collision costs one more inspection, even though we computed the home slot only once.

    Stop at the first empty slot

    Slot 3 is empty. Store 17 there. The insertion inspected three slots and changed one. A later lookup for 17 can start at slot 1 and repeat those comparisons until it finds the key in slot 3. In this table an empty slot also ends an unsuccessful lookup, because insertion would have used that slot before probing farther. Open Data Structures on linear probing

    What if slot 3 already holds 7?

    Try the second starting table. The home slot for 17 is still 1, but now the first three probes all meet a resident. Predict the next slot before advancing. The rule is to add one to the current address and take the remainder modulo four. At the end of the array, that arithmetic brings the probe back to the beginning.
